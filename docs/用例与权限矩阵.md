## 一、核心业务权限

以下按单个角色列出权限。
用户具有多个角色时，仍须遵守禁止本人审批、
部门数据隔离及业务状态约束。

| 操作 | 普通员工 | 部门审批人 | 资产管理员 | 系统管理员 |
|---|---|---|---|---|
| 查询可领用资产 | 允许 | 需兼有员工角色 | 允许 | 不默认授予 |
| 查看本人申请及领用记录 | 允许 | 需兼有员工角色 | 需兼有员工角色 | 需兼有员工角色 |
| 提交领用申请 | 允许 | 需兼有员工角色 | 需兼有员工角色 | 需兼有员工角色 |
| 提交归还申请 | 仅本人当前领用资产 | 同员工规则 | 同员工规则 | 同员工规则 |
| 查看部门待审批申请 | 禁止 | 仅本部门 | 禁止 | 禁止 |
| 批准或驳回领用申请 | 禁止 | 仅本部门，且禁止本人审批 | 禁止 | 禁止 |
| 新增及维护资产档案 | 禁止 | 禁止 | 允许 | 不默认授予 |
| 确认资产发放 | 禁止 | 禁止 | 允许 | 不默认授予 |
| 确认资产归还接收 | 禁止 | 禁止 | 允许 | 不默认授予 |
| 管理用户、部门及角色 | 禁止 | 禁止 | 禁止 | 允许 |

说明：
“同员工规则”要求用户兼有员工角色。
系统管理员不因其管理身份自动拥有业务审批和资产操作权限。

### 多角色与业务详情访问规则

1. 用户具有多个角色时，按各角色明确授予的权限合并。
   表中的“禁止”表示该角色本身不授予此项权限，
   不否定用户通过其他角色获得的权限。

2. 禁止本人审批、部门数据隔离、记录归属及业务状态约束，
   不因用户具有多个角色而失效。

3. 同时具有普通员工和资产管理员角色的用户，
   查询资产时可以使用资产管理员的数据范围，
   不受普通员工仅查询闲置资产的限制。

4. 普通员工可以查看本人申请和领用记录中的关联资产摘要，
   即使该资产当前已经不再闲置。
   摘要仅包含编号、名称、类别等业务必要信息，
   不因此获得完整资产档案的访问权限。

5. 部门审批人可以在本部门申请详情中查看审批所需的
   申请人、资产编号、名称、类别及领用用途，
   不要求其兼有普通员工角色。

6. 资产管理员可以查看办理发放和归还接收所必需的
   申请、审批结果及领用记录。
   此权限不赋予其领用审批权限。

7. 上述业务详情访问须先校验对应申请或记录的访问权限，
   不得仅凭资产编号绕过权限检查。

## 二、服务端校验要求

1. 受保护操作必须检查登录状态。
2. 每个操作必须检查角色权限。
3. 使用申请编号或领用记录编号访问数据时，
   必须检查其归属，不能仅判断记录是否存在。
4. 部门审批人只能审批本部门的申请，且不能审批本人申请。
5. 归还申请的提交人必须是当前领用人。
6. 资产发放与归还接收必须同时校验业务状态。
7. 页面隐藏按钮不能替代服务端权限校验。

## 四、核心用例

### UC01 提交资产领用申请

**参与者：** 具有普通员工角色的已登录用户。  
**对应验收标准：** AC03、AC08。

#### 前置条件

1. 用户已登录，具有普通员工角色，并已归属部门。
2. 目标资产存在，当前状态为“闲置”。
3. 当前用户对该资产没有处于“待审批”或“待发放”的申请。

#### 输入信息

- 资产编号；
- 领用用途：必填，去除首尾空白后为1～200个字符。

申请人身份、所属部门和提交时间由服务端确定，
不采用客户端提交的身份信息。

#### 正常流程

1. 员工查询可领用资产，选择目标资产。
2. 填写领用用途并提交。
3. 服务端校验登录身份、角色权限和输入内容。
4. 服务端重新检查资产状态及重复申请。
5. 创建“待审批”的领用申请，保存申请人、部门、
   资产、用途和提交时间。
6. 返回申请成功结果，员工可在本人申请列表查看记录。

#### 异常流程

| 情况 | 处理结果 |
|---|---|
| 未登录 | 拒绝提交，要求登录 |
| 没有员工角色 | 拒绝提交 |
| 用户未归属部门 | 拒绝提交，提示先完善部门信息 |
| 资产不存在 | 拒绝提交，提示资产不存在 |
| 资产不再闲置 | 拒绝提交，提示刷新资产信息 |
| 用途为空或超过200字符 | 拒绝提交，提示输入要求 |
| 已有待审批或待发放申请 | 拒绝重复创建，提示查看已有申请 |
| 数据保存失败 | 回滚本次操作，不留下不完整申请 |

#### 后置条件

1. 成功时新增一条“待审批”申请。
2. 提交申请不占用资产，不创建领用记录。
3. 不同员工可以申请同一闲置资产；
   最终是否能够发放，在发放时重新校验。
4. 失败时不新增申请，也不改变资产状态。

#### 验证要点

- 合法申请能够保存，申请人取自当前登录用户。
- 用途为空、全空白或超过200字符时被拒绝。
- 同一员工连续提交或并发提交同一资产申请，
  最多创建一条未结束申请。
- 修改请求中的申请人信息不能冒用其他用户。
- 申请提交成功后，资产仍为闲置。

### UC02 审批资产领用申请

**参与者：** 具有部门审批人角色的已登录用户。  
**对应验收标准：** AC04、AC08。

#### 前置条件

1. 用户已登录，具有部门审批人角色。
2. 目标申请存在，状态为“待审批”。
3. 申请中记录的部门与审批人的所属部门一致。
4. 审批人不是申请人本人。

#### 输入信息

- 申请编号；
- 审批结果：批准或驳回；
- 审批意见：最多200个字符。
  驳回时必填，去除首尾空白后不得为空；
  批准时可以不填。

审批人身份及审批时间由服务端确定。

#### 正常流程

1. 审批人打开本部门的待审批申请列表。
2. 查看申请人、资产和领用用途。
3. 选择批准或驳回，填写审批意见并提交。
4. 服务端校验身份、部门范围及禁止本人审批的规则。
5. 服务端校验申请仍为“待审批”。
6. 在同一事务中更新申请并保存审批操作日志：
    - 批准：申请变为“待发放”；
    - 驳回：申请变为“已驳回”。
7. 保存审批人、审批时间及审批意见，返回处理结果。

#### 异常流程

| 情况 | 处理结果 |
|---|---|
| 未登录或没有审批角色 | 拒绝操作 |
| 申请不存在 | 拒绝操作 |
| 申请不属于审批人所在部门 | 拒绝访问及审批 |
| 审批人就是申请人 | 拒绝审批，即使同时具有其他管理角色 |
| 申请已被审批或取消 | 拒绝操作，提示刷新 |
| 审批结果不是批准或驳回 | 拒绝提交 |
| 驳回原因为空或意见超过200字符 | 拒绝提交，提示输入要求 |
| 数据或日志保存失败 | 回滚本次审批 |

#### 后置条件

1. 成功时，申请进入“待发放”或“已驳回”状态。
2. 审批不会改变资产状态，也不会创建领用记录。
3. 批准不代表资产已被预留，实际发放时必须重新检查。
4. 失败时，申请及审批记录保持操作前的状态。

#### 验证要点

- 本部门审批人可以处理其他员工的待审批申请。
- 跨部门访问、跨部门审批和本人审批均被拒绝。
- 重复点击或并发审批时，最多一次状态转换成功，
  不得覆盖已经生效的审批结果。
- 驳回原因必填，审批意见长度限制有效。
- 修改请求中的审批人信息不能冒用他人身份。
- 申请状态更新与审批日志保存保持事务一致性。

### UC03 确认资产发放

**参与者：** 具有资产管理员角色的已登录用户。  
**对应验收标准：** AC05、AC06、AC08、AC09。

#### 前置条件

1. 用户已登录，具有资产管理员角色。
2. 目标领用申请存在，状态为“待发放”。
3. 对应资产存在，当前状态为“闲置”。
4. 该资产不存在尚未结束的有效领用记录。

#### 输入信息

- 领用申请编号。

资产及领用人从申请记录中取得。
操作人身份和发放时间由服务端确定，
不采用客户端提交的领用人或资产状态。

#### 正常流程

1. 资产管理员打开待发放申请列表。
2. 核对申请及实物交接情况，提交发放确认。
3. 服务端校验身份、权限及申请状态。
4. 在数据库事务中重新检查资产状态，
   并通过并发控制防止同一资产被重复发放。
5. 将资产状态更新为“在用”。
6. 创建有效领用记录，关联资产、申请及领用人。
7. 将申请状态更新为“已发放”。
8. 保存发放操作日志。
9. 提交事务，返回发放成功结果。

#### 异常流程

| 情况 | 处理结果 |
|---|---|
| 未登录或没有资产管理员角色 | 拒绝操作 |
| 申请或对应资产不存在 | 拒绝操作 |
| 申请不是待发放状态 | 拒绝操作，提示刷新 |
| 资产已在用、维修中或已报废 | 拒绝发放 |
| 资产已有有效领用记录 | 拒绝发放，提示检查资产记录 |
| 并发操作中其他请求已先完成发放 | 当前请求失败，不创建领用记录 |
| 状态、领用记录或日志保存失败 | 回滚整个发放事务 |

#### 后置条件

1. 成功时，资产为“在用”，申请为“已发放”，
   且该资产只有一条有效领用记录。
2. 资产状态、申请状态、领用记录和发放日志保持一致。
3. 失败时，不留下本次操作造成的部分更新。
4. 同一资产的其他待发放申请不自动标记为已发放。
   它们再次发放时仍须重新检查资产可用性。

#### 验证要点

- 合法发放后，资产、申请、领用记录和日志均正确。
- 对同一申请重复提交，不产生重复领用记录。
- 两个管理员并发发放同一资产时，最多一次成功。
- 对同一资产的不同待发放申请进行竞争发放，
  同样最多一次成功。
- 普通员工和部门审批人不能直接调用发放接口。
- 客户端篡改领用人信息不能改变申请中的领用人。
- 模拟事务中途失败时，不留下部分更新。

### UC04 提交资产归还申请

**参与者：** 具有普通员工角色的已登录用户。  
**对应验收标准：** AC07、AC08。

#### 前置条件

1. 用户已登录，具有普通员工角色。
2. 目标领用记录存在且尚未结束。
3. 当前用户为该记录的领用人，资产状态为“在用”。
4. 该领用记录不存在“待确认”的归还申请。

#### 输入信息

- 领用记录编号。

申请人身份和提交时间由服务端确定，
资产从领用记录中取得。

#### 正常流程

1. 员工在本人领用列表中选择需要归还的资产。
2. 提交归还申请。
3. 服务端校验身份、记录归属、资产状态及重复申请。
4. 创建“待确认”的归还申请，关联原领用记录。
5. 返回提交成功结果。

#### 异常流程

| 情况 | 处理结果 |
|---|---|
| 未登录或没有员工角色 | 拒绝提交 |
| 领用记录不存在或不属于当前用户 | 拒绝操作 |
| 领用记录已结束或资产不在用 | 拒绝提交，提示刷新 |
| 已存在待确认的归还申请 | 拒绝重复创建 |
| 数据保存失败 | 回滚本次操作 |

#### 后置条件

1. 成功时新增一条“待确认”的归还申请。
2. 资产仍为“在用”，原领用记录保持有效。
3. 只有资产管理员确认接收后，才结束领用。

#### 验证要点

- 当前领用人可以提交归还申请。
- 修改领用记录编号不能替他人提交归还申请。
- 连续或并发提交时，最多创建一条待确认申请。
- 提交申请不会提前释放资产。

### UC05 确认资产归还接收

**参与者：** 具有资产管理员角色的已登录用户。  
**对应验收标准：** AC07、AC08、AC09。

#### 前置条件

1. 用户已登录，具有资产管理员角色。
2. 归还申请存在，状态为“待确认”。
3. 关联领用记录尚未结束，且与资产当前有效领用记录一致。
4. 对应资产状态为“在用”。
5. 管理员已核对实物，本用例仅处理可正常归还的资产。

#### 输入信息

- 归还申请编号。

操作人身份和接收时间由服务端确定。

#### 正常流程

1. 管理员查看待确认归还申请并核对实物。
2. 提交接收确认。
3. 服务端校验权限、申请状态及关联记录的一致性。
4. 在数据库事务中，通过并发控制确保接收只能生效一次。
5. 结束原领用记录，记录实际归还时间。
6. 将资产状态恢复为“闲置”，清除当前领用关系。
7. 将归还申请状态更新为“已完成”。
8. 保存归还接收操作日志。
9. 提交事务，返回接收成功结果。

#### 异常流程

| 情况 | 处理结果 |
|---|---|
| 未登录或没有资产管理员角色 | 拒绝操作 |
| 归还申请不存在或不是待确认状态 | 拒绝操作 |
| 领用记录已结束或关联关系不一致 | 拒绝操作，提示检查记录 |
| 资产不是在用状态 | 拒绝接收，提示检查资产状态 |
| 其他请求已完成同一归还接收 | 当前请求失败，不重复更新 |
| 任一状态、记录或日志保存失败 | 回滚整个接收事务 |

#### 后置条件

1. 成功时，归还申请为“已完成”，原领用记录已结束，
   资产恢复“闲置”。
2. 原领用申请仍保留“已发放”状态，
   是否已归还通过关联领用记录判断。
3. 历史领用和归还记录保留，不进行物理删除。
4. 失败时，不留下本次操作造成的部分更新。

#### 验证要点

- 合法接收后，资产、归还申请及领用记录一致。
- 重复或并发接收最多一次成功。
- 旧归还申请不能结束资产后续产生的新领用记录。
- 普通员工不能直接确认接收或释放资产。
- 模拟事务中途失败时，所有相关修改回滚。

### UC06 新增资产档案

**参与者：** 具有资产管理员角色的已登录用户。  
**对应验收标准：** AC01、AC08、AC09。

#### 前置条件

用户已登录，具有资产管理员角色。

#### 输入信息

| 字段 | 校验规则 |
|---|---|
| 资产编号 | 必填，去除首尾空白后1～50字符，全局唯一 |
| 名称 | 必填，去除首尾空白后1～100字符 |
| 类别 | 必填，必须为有效类别 |
| 购置日期 | 必填，不得晚于当天 |
| 原值 | 必填，非负数，最多两位小数 |
| 存放位置 | 必填，去除首尾空白后1～100字符 |

初始状态由服务端设为“闲置”，不接受客户端指定状态。

#### 正常流程

1. 管理员填写资产信息并提交。
2. 服务端校验权限、字段及编号唯一性。
3. 在同一事务中保存资产档案和建档操作日志。
4. 返回创建成功结果及资产标识。

#### 异常流程

- 未登录或没有资产管理员角色：拒绝操作。
- 必填项缺失、格式不合法或类别无效：拒绝保存并提示。
- 编号重复：拒绝创建，不覆盖已有资产。
- 并发创建相同编号：最多一条成功。
- 档案或日志保存失败：回滚本次创建。

#### 后置条件

成功时新增一条闲置资产及对应操作日志；
失败时不留下不完整档案。

#### 验证要点

- 合法信息可保存，资产初始状态为闲置。
- 重复编号、负数金额和非法日期被拒绝。
- 字段长度及金额小数位限制有效。
- 篡改请求中的资产状态不能直接创建在用资产。
- 无权限用户不能通过直接调用接口完成建档。

### UC07 查询资产

**参与者：** 具有普通员工或资产管理员角色的已登录用户。  
**对应验收标准：** AC02、AC08。

#### 查询条件

- 资产编号：精确匹配；
- 资产名称：包含匹配；
- 类别：精确匹配；
- 状态：精确匹配，仅资产管理员可选择；
- 页码和每页条数：默认每页20条，最多100条。

多个条件同时填写时，按“同时满足”进行筛选。
列表默认按资产编号升序排列。

#### 数据范围

1. 普通员工仅能查询闲置资产。
2. 普通员工查看编号、名称、类别、位置及状态，
   不返回原值和购置日期。
3. 资产管理员可以查询所有状态的资产，
   并查看完整资产档案。
4. 其他角色需兼有上述角色，才能使用相应查询功能。
5. 本人已领用资产通过“本人领用记录”查看，
   不依赖闲置资产查询。

#### 正常流程

1. 用户输入查询条件。
2. 服务端校验登录身份、角色及查询参数。
3. 服务端根据角色施加数据范围限制。
4. 按条件查询并返回分页结果。

#### 异常流程

- 未登录或没有查询权限：拒绝访问。
- 参数格式错误或分页超出允许范围：拒绝并提示。
- 没有匹配数据：返回空列表。
- 普通员工请求非闲置资产：拒绝该查询条件，
  不扩大其数据范围。

#### 验证要点

- 单条件和组合条件均能正确筛选。
- 分页及排序结果稳定。
- 员工不能通过篡改状态参数查询全部资产。
- 员工直接访问非闲置资产详情时同样受到限制。
- 返回数据不包含当前角色无权查看的字段。

### UC08 修改资产档案

**参与者：** 具有资产管理员角色的已登录用户。
**关联工作项：** [3.4] 实现资产建档与信息维护。
**对应验收标准：** AC08、AC09，并补充档案修改验收条件。

#### 前置条件

1. 用户已登录，具有资产管理员角色。
2. 目标资产存在，且未报废。

#### 输入及修改范围

- 资产唯一标识；
- 名称、类别、购置日期、原值、存放位置；
- 用于识别并发修改的版本信息。

本版本资产编号创建后不可修改。
可修改字段沿用UC06的必填、长度、金额及日期校验规则。

资产状态、当前领用人及历史业务记录，
不得通过档案修改接口直接改变。
资产状态只能通过对应业务流程转换。

#### 正常流程

1. 管理员打开资产档案，获取当前信息及版本。
2. 修改允许编辑的字段并提交。
3. 服务端校验权限、资产状态和字段内容。
4. 检查档案是否已被其他操作更新。
5. 在同一事务中保存修改并记录操作日志。
6. 日志记录操作人、时间、资产及变更字段的修改前后值。
7. 返回修改成功结果。

#### 异常流程

| 情况 | 处理结果 |
|---|---|
| 未登录或没有资产管理员角色 | 拒绝操作 |
| 资产不存在 | 拒绝修改 |
| 资产已报废 | 拒绝修改，保留历史档案 |
| 字段校验失败 | 拒绝保存并提示 |
| 请求试图修改编号、状态或领用人 | 拒绝修改 |
| 档案已被其他操作更新 | 拒绝覆盖，提示刷新后重新编辑 |
| 档案或日志保存失败 | 回滚本次修改 |

#### 后置条件

1. 成功时，仅更新允许修改的档案字段。
2. 不改变资产状态、当前领用关系及历史业务记录。
3. 修改日志与档案更新保持一致。
4. 失败时，不留下本次操作造成的部分更新。

#### 验证要点

- 合法修改能够保存并生成包含前后值的日志。
- 普通员工、仅有审批角色或系统管理员角色的用户不能修改。
- 非法金额、日期和字段长度被拒绝。
- 篡改请求不能直接改变资产状态或领用人。
- 两个管理员基于同一版本修改时，
  后提交的旧版本不能覆盖已保存的新版本。
- 已报废资产不可修改。
- 模拟日志保存失败时，档案修改同时回滚。

### UC09 取消本人申请

**参与者：** 具有普通员工角色的已登录用户。
**关联工作项：** [3.6] 实现领用申请、[3.9] 实现归还申请与接收。
**对应验收标准：** AC08、AC09，并补充申请取消验收条件。

#### 前置条件

1. 用户已登录，具有普通员工角色。
2. 目标申请存在，申请人为当前用户。
3. 申请处于允许取消的状态：
    - 领用申请：待审批或待发放；
    - 归还申请：待确认。

#### 输入信息

- 申请类型：领用或归还；
- 申请编号。

取消人身份和取消时间由服务端确定。

#### 正常流程

1. 员工在本人申请列表中选择取消。
2. 服务端校验身份、申请归属及当前状态。
3. 在同一事务中将申请更新为“已取消”，
   保存取消时间及操作日志。
4. 返回取消成功结果。

#### 状态及数据规则

1. 取消领用申请不改变资产状态，不创建或结束领用记录。
2. 取消归还申请后，资产仍为“在用”，原领用记录继续有效。
3. 已取消的申请不可恢复，历史申请及审批记录保留。
4. 员工可以重新提交申请，但须重新满足提交条件。
5. 已发放、已驳回、已完成或已取消的申请不能再次取消。
6. 已发放资产如需归还，必须走归还申请及接收流程。

#### 异常流程

| 情况 | 处理结果 |
|---|---|
| 未登录或没有员工角色 | 拒绝操作 |
| 申请不存在或不属于当前用户 | 拒绝操作 |
| 申请类型不合法 | 拒绝操作 |
| 当前状态不允许取消 | 拒绝操作，提示刷新 |
| 申请在操作期间被其他请求更新 | 本次取消失败，提示刷新后重试 |
| 状态或日志保存失败 | 回滚本次取消 |

#### 并发规则

1. 取消与审批、发放或归还接收并发发生时，
   必须检查读取后的申请是否已被更新，
   不得覆盖其他操作已经生效的结果。
2. 取消先成功时，后续审批、发放或接收请求必须失败。
3. 发放或归还接收先成功时，取消必须失败。
4. 审批先成功时，本次基于旧状态的取消失败；
   刷新后若为“待发放”，允许重新取消；
   若为“已驳回”，不允许取消。

#### 后置条件

成功时申请为“已取消”，且存在取消操作日志。
失败时不留下本次操作造成的部分更新。

#### 验证要点

- 员工只能取消本人的申请。
- 各允许状态可以取消，各终结状态拒绝取消。
- 取消归还申请不会释放资产或结束领用记录。
- 重复取消不产生重复操作记录。
- 并发取消与其他业务操作不会互相覆盖。
- 取消后重新申请仍须通过资产状态及重复申请检查。

### UC10 用户登录与退出

**参与者：** 系统用户。  
**关联工作项：** [3.3] 实现用户登录与权限控制。  
**对应验收标准：** AC08。

#### 输入信息

- 用户名；
- 密码。

本版本不提供公开注册。
账号由初始化数据或系统管理员建立，
账号管理的具体实现边界另行明确。

#### 登录正常流程

1. 用户打开登录页面，输入用户名和密码。
2. 服务端校验输入、账号状态及密码。
3. 验证通过后建立登录会话，并更新会话标识。
4. 根据用户权限显示可访问的功能入口。
5. 后续受保护请求仍须由服务端检查权限。

#### 登录异常流程

| 情况 | 处理结果 |
|---|---|
| 用户名或密码为空 | 拒绝登录，提示填写 |
| 用户名不存在、密码错误或账号被停用 | 统一提示“用户名或密码错误，或账号不可用” |
| 登录失败 | 不建立已认证会话 |
| 未登录访问受保护页面 | 引导登录，不返回受保护数据 |
| 已登录但没有操作权限 | 拒绝操作，不改变业务数据 |

#### 退出流程

1. 用户提交退出请求。
2. 服务端使当前登录会话失效。
3. 用户返回登录页面。
4. 退出后再次请求受保护资源，必须重新登录。

#### 会话与安全规则

1. 密码只保存不可逆的安全哈希，不保存明文。
2. 密码不写入日志、网址参数或操作审计内容。
3. 登录会话连续30分钟无请求后失效。
4. 使用会话Cookie认证时，改变数据的请求须进行CSRF校验；
   退出请求同样受保护。
5. 公网部署使用HTTPS传输登录凭据和会话信息。
6. 页面显示权限不能替代服务端接口权限校验。

#### 验证要点

- 有效账号和正确密码可以登录。
- 错误凭据及不可用账号不能登录。
- 不同角色只能完成获授权的操作。
- 登录后会话标识与登录前不同。
- 退出或会话超时后，原会话不能继续访问受保护资源。
- 缺少或伪造CSRF令牌的数据修改请求被拒绝。
- 日志和数据库中不出现明文密码。

## 五、操作日志查看规则

关联工作项：[3.10] 实现关键操作日志。

1. 资产管理员可以分页查看资产建档、档案修改、
   审批、发放、归还接收及申请取消的业务操作日志。
2. 日志包含操作人、操作时间、操作类型、对象标识及结果；
   档案修改另外记录变更字段的前后值。
3. 日志查询支持按操作时间范围、操作类型和对象标识筛选。
4. 普通员工及部门审批人通过获授权的申请详情查看业务进展，
   不默认拥有全局日志查询权限。
5. 系统管理员不默认拥有业务日志查看权限，
   兼有资产管理员角色时按该角色授权访问。
6. 所有角色均不能通过业务页面或接口修改、删除操作日志。
7. 成功业务操作的审计日志与业务更新在同一事务中保存。
   失败请求如需记录，写入独立的技术或安全日志；
   不要求被回滚的业务事务留下成功审计记录。
8. 日志不得记录密码、会话令牌等认证敏感信息。

验收时验证有权限查询、越权拒绝、筛选分页、
日志不可篡改，以及业务更新与成功审计日志的一致性。

## 六、账号与基础数据管理

本版本实现基础在线管理，仅系统管理员可操作。

| 功能 | 实现范围 | 验收条件 |
|---|---|---|
| 用户管理 | 新增用户、修改姓名和所属部门、启用或停用 | 用户名唯一；停用后不能登录，已有会话不能继续访问受保护功能 |
| 角色分配 | 为用户分配或移除已有角色 | 不提供自定义权限编辑；权限变更在后续请求中生效 |
| 部门管理 | 新增、修改部门名称 | 部门名称唯一；已关联业务的数据不物理删除 |
| 类别管理 | 新增、修改资产类别名称 | 类别名称唯一；已被资产引用的类别不物理删除 |

公共规则：
- 所有操作在服务端校验系统管理员权限。
- 用户密码以安全哈希保存，不在查询结果或日志中返回。
- 保留至少一个启用的系统管理员，禁止停用或降权最后一个管理员。
- 记录用户维护、角色变更及基础数据修改的管理审计日志，
  仅系统管理员可查看。
- 修改用户部门不改变历史申请中保存的部门信息。
- 初始化脚本仍提供首次登录所需的管理员和演示数据。

暂不实现公开注册、找回密码、批量导入及复杂组织层级。
